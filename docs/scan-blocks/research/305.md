## 1. Model facts (ESDNet)

- **F1 (found, A).** "Params (M)" for ESDNet is **5.934** (Table 2); ESDNet-L has **10.623 M** parameters.
- **F2 (found, A).** Speed: "Surprisingly, our ESDNet only needs 17ms (i.e., 60fps) to process a standard 4K resolution image." The GPU is "NVIDIA RTX 3090 GPU", and the resolution is 3840×2160.
- **F3 (found, A).** FLOPs for ESDNet are not given as a number in the text. Figure 3 plots "MultiAdds" without a value for ESDNet in the text (the fetch could not read the figure).
- **F4 (found, A).** Dataset: "Our dataset contains 5,000 image pairs in total," split 4,500 for training and 500 for validation (Section 3.1). The introduction calls the same 500 "testing image pairs": the paper is inconsistent on this.
- **F5 (found, B).** The repository lists "Apache-2.0 license" as a label, with a LICENSE.md file. The page has no licence section in the README. The LICENSE.md text was not read.
- **F6 (found, B).** Weights: "We provide pre-trained models on four datasets" (UHDM, FHDMi, TIP2018, LCDMoire), eight checkpoints (ESDNet and ESDNet-L for each), hosted on Google Drive, downloaded by `bash scripts/download_model.sh`. The page states no licence for the weights.
- **F7 (found, B).** UHDM: "We provide the 4K dataset UHDM for you to evaluate a pretrained model or train a new model." The repository shows no usage terms for the dataset.
- **F8 (found, B).** The HF demo note: "Note the demo runs on CPU, so the inference may cost 80s per 4K image." No CPU model is named.
- **F9 (found, C).** Operators used by ESDNet: `nn.Conv2d` (dilated in several blocks), strided conv (`kernel_size=3, stride=2`), `F.pixel_unshuffle(x, 2)` in `Encoder.forward`, `F.pixel_shuffle(out, 2)` in `Decoder_Level.forward`, bilinear `F.interpolate`, `nn.AdaptiveAvgPool2d((1, 1))`, ReLU, sigmoid, `torch.cat`, `torch.chunk`. "Custom ops: None." `nn.ConvTranspose2d` appears only in weight initialisation. The file header has no licence comment.
- **F10 (found, E).** rten: "- [ ] SpaceToDepth" (not supported); "- [x] DepthToSpace" (supported); Reshape, Transpose, Resize, Sigmoid, Gelu are checked as supported. The page carries no date.

**Worked out (size).** 5.934 × 10^6 parameters × 4 bytes = 23.7 MB as FP32; × 2 bytes = 11.9 MB as FP16. These are weight sizes only, before any graph overhead, which is **not known**.

**Worked out (pixels).** A 4K frame is 3840 × 2160 = 8,294,400 px. A 1024-px long side at 16:9 is 1024 × 576 = 589,824 px, 14.1 times fewer; at 4:3 (1024 × 768 = 786,432 px) it is 10.5 times fewer. These are pixel ratios. ESDNet's cost per pixel is **not known** (F3), so no time can be worked out from them.

**Worked out (speed figures).** 8,294,400 px / 0.017 s = 488 million px per second on an RTX 3090 (F2, GPU). 8,294,400 px / 80 s = 0.10 million px per second on the demo's CPU (F8, unnamed CPU). These two rates are for different hardware and cannot be converted to a phone; no phone figure follows.

## 3. Detection and classical removal (the spec's own method)

- **F12 (found, D).** The classical literature has a frequency-domain peak method: "We propose a peak-filtering algorithm to remove multiple uniform peaks in the frequency domain," and "First, the largest peak is located in the entire frequency domain." (MDPI, Mathematics 2024, 12(6), 846, CC BY.) The text read gave no quantitative results (only section headings for "Experimental Results", "Ablation Study" and "Comparison with State-of-the-Art Methods"), no dataset and no runtime.
- **Not known:** whether the spec's detector thresholds (peaks above 8× the annulus median, the 40% rule, the 3-bin width) work on real screen photos. No source found gives those numbers or a precision and recall on screen photos. The spec proposes them without a source.
- **Not known:** whether Gaussian notches on the detected peaks keep text sharpness within 10%. No source found.
- **Not known:** whether a descreening low-pass suits halftones. No source found.
- **Not known:** whether a live capture hint (S09) removes most moiré. No source found; the spec asks the owner to test it by hand.

## 4. Feasibility of the learned route

- The ESDNet operators (F9) are standard. The export's risk is the same as for DocRes (#304): `F.pixel_unshuffle` may export as **SpaceToDepth**, which rten 0.26 does not list as supported (F10). Whether the exporter emits SpaceToDepth for this layer is **not known**: no export of ESDNet was found, and I did not run one.
- Phone time at 1024 px: **not known**. F2 is a GPU figure at 4K; F8 is a CPU demo at 4K with unnamed hardware. The spec's 1024-px measurement is the only source that can settle it.

## 5. Recommendation

- **(a) Detector and capture hint first: go, but only as a research step.** The detector and its test are the cheap, learned-free part. It goes ahead only if precision and recall on the owner's screen photos, against all other kinds, are both high enough for the team to choose. Those numbers are **not known** and must come from the owner's data.
- **(b) Classical removal as a "Screen" look: go only if** the notch filter reduces the visible grating by at least the spec's 80% and keeps text sharpness within 10% on the owner's own screen photos. No source found supports either number.
- **(c) A model as an optional pack: go only if** the weights' licence is stated to allow redistribution (F6, not stated), the ONNX export loads in rten 0.26 without SpaceToDepth (F10, not known), and the phone time at 1024 px is measured. Until then, **do not**.
- **(d) Drop:** not recommended by this research, because nothing found shows moiré removal is infeasible.

## 6. Cheapest experiment that settles what is not known

1. **Detector (desktop, no weights).** Generate the spec's synthetic gratings and plain pages in code (the spec's tests), and run the FFT detector on the owner's screen photos. Number that decides: the detector's recall on screen photos must clear the spec's 40%-of-tiles rule without firing on text pages (false positives on the spec's negative set).
2. **Licence (no compute).** Read the Google Drive folder's readme or ask the authors (the repository's issue tracker) for the weights' terms. This alone decides whether a model can be shipped.
3. **Export check (PC).** Export ESDNet at 1024 px to ONNX, load it in rten 0.26 on the PC, and count unsupported operators and SpaceToDepth nodes. The number that decides: zero unsupported operators.
4. **Phone timing (only after 2 and 3 pass).** One inference at 1024 px with four threads: seconds and peak memory. Decides the option (c).
