**Worked out (licence).** Code: MIT by label (F2), text not read. Weights: no licence stated by the authors (F4, F7). The mirrors' MIT claim (F5) is not from the authors and cannot be relied on for an app that redistributes the file. The training-data terms are not known for any set except that Doc3D needs a login (F10).

**Decision rule applied.** The project's rule says a licence that forbids redistribution inside an app is a blocker. The authors have stated no licence for the weights, so whether they allow redistribution is **not known**. Under that rule it is a blocker for shipping, including as an optional download, until the authors or the mirrors' terms are confirmed. Personal, non-commercial use of a file the authors publish is the minimum bar; I did not find a source that says the authors grant even that in writing.

## 2. Model facts

- **F11 (found, B, supplementary Table 1).** DocRes has **15.2 M** parameters and **183.0 GFLOPs**. The paper "does not state the input size used for this figure" (the tool's note on the page).
- **F12 (found, B).** Training: "Images of deshadowing, appearance enhancement, deblurring, and binarization tasks are randomly cropped as patches with a size of 256×256".
- **F13 (found, B).** Inference: "DocRes can support inputs of up to 1600×1600 and adapt to inputs with variable resolutions."
- **F14 (found, B).** Speed: the paper reports none. The only hardware is "We train our model on 8 NVIDIA A6000 GPUs for 100,000 steps with a global batch size of 80."
- **F15 (found, D).** The mirror `docres.pkl` is **183 MB**, and its file page lists "pickle imports" and marks the file "Safe" (https://huggingface.co/DaVinciCode/doctra-docres-main/tree/main). Mirror size, not the authors' file.
- **F16 (found, C).** The inference code loads the weights with `torch.load(args.model_path, map_location='cpu')['model_state']` and a default path `./checkpoints/docres.pkl`.
- **F17 (not known).** No ONNX export of DocRes was found. A search for "DocRes onnx export document restoration" returned only the paper, the repository and Space pages, none of which mention ONNX. I did not check ONNX model hubs beyond that search.

**Worked out (size).** 15.2 M parameters × 4 bytes = 60.8 MB as FP32; × 2 bytes = 30.4 MB as FP16. The spec's "about 61 MB" and "about half" agree with that. The mirror pickle is 183 MB, about 3.0 times 60.8 MB. The pickle may hold more than weights (what it holds is **not known**). So the exported ONNX size must be measured, not taken from the spec.

**Worked out (compute).** The 183.0 GFLOPs (F11) is for an input size not stated. Two cases:
- If it is a 256×256 input (65,536 px): 183 × 10^9 / 65,536 = 2.79 × 10^6 FLOP per pixel. At the spec's 384×512 (196,608 px) that is 549 GFLOP per pass.
- If it is 512×512 (262,144 px): 183 × 10^9 / 262,144 = 0.70 × 10^6 FLOP per pixel. At 384×512 that is 137 GFLOP per pass.

So one pass at 384×512 is **137 to 549 GFLOP**; the spec's two passes give **274 to 1,097 GFLOP** per page. If the 183 figure counts multiply-adds rather than FLOP, double these. At 512×704 (360,448 px, 1.83 times 384×512) one pass is 251 to 1,006 GFLOP.

**Worked out (the spec's gate).** A 6 s gate for 274 to 1,097 GFLOP needs a sustained rate of 274 / 6 = 46 GFLOP/s up to 1,097 / 6 = 183 GFLOP/s across the whole page. What a phone CPU sustains under rten 0.26 with four threads is **not known**: I found no source for it. This is the number the spec's measurement exists to find.

## 3. Pre- and post-processing facts (from the inference code, C)

- **F18 (found, C).** Deshadowing prompt: `dilated_img = cv2.dilate(plane, np.ones((7,7), np.uint8))` then `bg_img = cv2.medianBlur(dilated_img, 21)`. The paper describes it as dilation "to eliminate the textual content" followed by a median filter (B).
- **F19 (found, C).** Appearance prompt: `diff_img = 255 - cv2.absdiff(plane, bg_img)`, then `cv2.normalize(... alpha=0, beta=255, NORM_MINMAX)` to 0–255. The paper gives it as Pdiff(Is) = 255 − abs(Is − Pbg(Is)) (B).
- **F20 (found, C).** Input scaling: `in_im = in_im / 255.0`; output `pred = torch.clamp(pred,0,1)`.
- **F21 (found, C).** Sizes: the deshadowing prompt is computed on `img = cv2.resize(img,(1024,1024))`; a long side above MAX_SIZE = 1600 is resized to 1600; otherwise `stride_integral(in_im, 8)` pads to a multiple of 8.

**Consequence for the port (worked out).** The spec says the prompt is computed "from the input image itself". The code computes the deshadowing background on a 1024×1024 resize, not on the 384×512 model input. The port's fixtures must use the same 1024×1024 step, or the prompt will not match the Python output. The spec's "Port the exact operations" line depends on this. Whether the upstream file does the same as the mirror is **not known** (F3-style fetch failure).

**Non-learned alternative, found in the same code.** Step 1 of the prompt is a 7×7 dilation and a 21-pixel median: a classical background estimate. The learned part adds only the restoration network on top of that prompt. So the background map that %%S12%% already plans is the non-learned counterpart of the deshadowing prompt.

## 4. Operators (rten 0.26, checklist E)

- **F22 (found, E).** "- [ ] SpaceToDepth" (not supported). "- [x] DepthToSpace (https://github.com/robertknight/rten/pull/468)" (supported).
- **F23 (found, E).** Checked as supported: LayerNormalization, Gelu, Erf, Reshape, MatMul, Softmax, Pad, Resize, Transpose, Split, Slice, Gather, Concat, ConvTranspose, Sigmoid, Mean, ReduceMean, Sqrt, Pow, Where, Expand, Tile.
- **F24 (found, E).** The page says: "Support for an operator does not mean that all attributes or data types listed in the current spec are supported." Attention is not an ONNX operator on the list; attention must be exported as MatMul and Softmax, which are supported (F23).
- **F25 (found, E).** The page carries no date.

**Worked out (operators).** Pixel shuffle exports as DepthToSpace (supported). Pixel unshuffle is the case the spec names: if the exporter emits SpaceToDepth, the export wrapper must rewrite it as reshape and transpose (also supported, F23). **Whether the exporter emits SpaceToDepth for this model is not known**: I did not find an export of DocRes or Restormer to ONNX to read. Restormer's downsampling uses pixel unshuffle (its own code, not read).

## 5. Third-party evidence on Restormer ONNX (not DocRes)

- **F26 (found, third party).** An ONNX export of a Restormer **denoising** model exists on Hugging Face (https://huggingface.co/efwfe/restomer). Its licence label is "License: openrail", not MIT. It lists FP32 105 MB, FP16 55 MB, opset 18, dynamic H and W "padded to multiple of 8". It reports "about 1,100 ms for a 512×512 input on CPU with FP16, versus about 1,700 ms for FP32" and "Actual performance depends on hardware." The CPU is not named.

**Worked out (use of F26).** It shows that a Restormer graph has been exported to ONNX by someone, which is evidence the path is possible. It does not give a DocRes time: it is a different variant, a different task, and the CPU is unknown. 512×512 is 262,144 px, against 196,608 px for 384×512 (ratio 1.33). Its 1.1 s figure must not be quoted as a DocRes speed.

## 6. Smaller alternatives

- **LP-IOANet** (Samsung, shadow removal for documents): "running real-time on a mobile device in four times the resolution" (arXiv abstract, https://arxiv.org/abs/2303.12862v1). The Samsung blog states "Runtime performance (at high-resolutions) on Samsung Galaxy S22 Ultra GPU" and "Runtime and memory are evaluated on RTX 3090 GPUs" (https://research.samsung.com/blog/LP-IOANet-Efficient-High-Resolution-Document-Shadow-Removal). **Found:** the phone figure is a GPU figure. **Not known:** parameter count, code, licence (no code link found in the abstract or the blog; search "LP-IOANet github code" returned none).
- **MatteViT** (arXiv 2512.08789, the spec's own lead): the abstract says "MatteViT achieves state-of-the-art performance" on RDD and Kligler and mentions "text edges and lines". **Not known:** code, parameters, runtime (the abstract states none). I did not read the full paper.

## 8. Recommendation

**Go only if:**
1. The authors (or a stated licence beside `docres.pkl`) grant rights to redistribute the weights, or the team accepts personal use only and keeps the model out of any release, including the optional download.
2. The export at 384×512 loads in rten 0.26 and reports no unsupported operator (the check in Section 4).
3. The phone measurement from the spec's gate is under 20 s per page at 384×512 (the spec's own thresholds: under 6 s for rten; 6 to 20 s only as a background option).

**Do not** ship it as an in-app download while item 1 is open.

## 9. Cheapest experiment that settles what is not known

1. **Licence (no compute).** Read the OneDrive folder's readme, or ask the authors in the repository's issue tracker, for the weights' terms. Decides items 1 and 2.
2. **Export and op check on a PC (no phone).** Verify the SHA-256 of `docres.pkl` first, then load it with `weights_only` semantics if possible (torch.load of an untrusted pickle runs code; this is my general knowledge, no source read). Export at 384×512, opset 17, then load the ONNX in rten 0.26 on the PC. The number that decides: the count of unsupported operators (must be 0) and the count of SpaceToDepth nodes (must be 0 or be rewritten).
3. **Phone timing (the spec's gate).** One inference at 384×512 with four threads: load time, peak memory, seconds per inference. Decides the three thresholds (6 s, 20 s).
4. **Fixture check.** Compute the two prompts with the 1024×1024 step (F21) and compare with the Python output; the spec's ≤ 1 grey level tolerance applies.
